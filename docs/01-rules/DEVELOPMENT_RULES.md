# Development Rules

## 1. Branch / Commit

구체적인 Git 전략은 기술 설계 단계에서 확정한다.

기본 원칙:
- 한 작업 단위에 집중된 커밋을 선호한다.
- 기능, 수정, 문서 변경의 의미가 커밋 메시지에서 드러나게 한다.
- 대규모 자동 포맷 변경을 기능 변경과 섞지 않는다.

## 2. Testing

- 기능 단위 테스트가 가능한 구조를 선호한다.
- 버그 수정은 가능하면 재현 테스트를 먼저 추가한다.
- RAG는 일반 단위 테스트 외에 별도의 평가 질문 세트를 유지한다.

## 3. Error Handling

- 사용자 입력 오류와 서버 오류를 구분한다.
- 오류를 무시하거나 빈 값으로 삼키지 않는다.
- Admin 작업에서 Index 실패 등 후속 처리 실패를 추적할 수 있어야 한다.

## 4. Security

- Admin 인증을 필수로 한다.
- Secrets는 환경 변수 등 외부 설정으로 관리한다.
- 사용자 입력 Markdown/HTML 렌더링 시 XSS 위험을 고려한다.
- 운영 로그에 Token/Secret/민감 Credential을 남기지 않는다.

## 5. Data Changes

- Schema 변경은 Migration을 사용한다.
- 원본 콘텐츠와 파생 RAG 데이터의 책임을 분리한다.
- 원본 데이터 변경 시 Re-index 흐름을 명확히 한다.
