## 개요

순찰 로봇 관제 시스템의 **PoC(실증) 프로젝트**입니다. 중앙 컨트롤 서버 1대와 여러 로봇으로 구성되고, 각 로봇 안에 자체 서버가 있어 중앙 서버와 통신하는 구조입니다. PoC 단계에서는 로봇 1대를 가정하고 진행했습니다.

정해진 구조 위에 기능을 얹는 일과, 아무것도 없는 상태에서 컴포넌트 경계를 나누는 일은 다릅니다. 이 프로젝트는 후자였습니다.

:::questions
- 폐쇄망에서 실시간 영상 관제를 어떻게 구현했나요?
- 중앙 서버와 로봇 사이의 책임을 어떻게 나눴나요?
:::

## 배경 · 문제

- **폐쇄망** — 네트워크가 제한된 환경이라 외부 인프라(시그널링 서버, TURN 등)를 전제할 수 없음
- **분산 구조** — 로봇마다 서버가 내장되므로 중앙과 엣지 사이의 책임 분배를 처음부터 정의해야 함
- **연결이 끊기는 것이 정상** — 로봇은 이동·충전·재부팅으로 상시 연결을 보장할 수 없음
- **PoC 스코프** — 다중 로봇 운영은 범위 밖

## 역할 · 기여도

| 컴포넌트 | 담당 |
|---|---|
| 중앙 통제 서버 (NestJS) | 본인 |
| 중앙 통제 웹 (관제) | 본인 |
| 로봇 내 컨트롤 페이지 | 본인 |
| 로봇 내 서버 | 의뢰자 |
| 네트워크 설계 | 의뢰자 |

본인이 개발한 NestJS 서버는 로봇에 내장되는 엣지 서버가 아니라 중앙 통제 서버입니다.

## 기술 선택 이유

**영상 전송에 WebSocket 채택** — HLS는 지연이 커서 관제 용도에 부적합했고, WebRTC는 시그널링·TURN 인프라가 필요한데 폐쇄망 구조에서 그 비용을 상쇄할 이득이 없었습니다. 이미 로봇 위치 전송용 WebSocket 연결이 있었기 때문에 동일 채널을 재사용했습니다.

프레임은 base64가 아니라 **바이너리로 전송**했습니다. base64 인코딩은 약 33%의 대역폭 오버헤드가 발생하는데, 폐쇄망에서 영상 스트림이 지속적으로 흐르는 구조라 그 손실을 감수할 이유가 없었습니다.

## 주요 작업

- **계층 간 책임 분배** — 스케줄의 등록·수정·삭제는 중앙 서버가 소유하고, 예정 시각에 로봇 서버로 명령을 전달하면 로봇이 태스크를 큐에 쌓아 순차 실행하는 구조로 나눔
- **실시간 영상 관제** — RTSP 스트림을 ffmpeg로 변환해 WebSocket으로 관제 웹에 전달
- **실시간 로봇 위치 렌더링**
- **카메라 자원 생명주기** — 카메라는 관제 요청이 있을 때만 활성화하고, 관제 웹 연결이 종료되면 중앙 서버가 이를 감지해 로봇 측 스트림을 해제. 순찰 로봇은 배터리가 곧 가동 시간이므로 시청자가 없는 동안 카메라와 인코딩 자원이 점유되지 않는 것을 요구사항으로 봄
- **Docker 기반 폐쇄망 배포 구성**

## 트러블슈팅

로봇은 전달받은 태스크를 스택에 쌓아 순차 실행합니다. A 작업이 끝나기 전에 B의 예정 시각이 되면, B는 A가 끝난 뒤에 실행됩니다. 즉 **UI에 등록한 시각은 실행 시각이 아니라 명령 전달 시각**입니다.

관제자는 "14시에 A구역 순찰"을 등록하면 14시에 순찰이 시작된다고 믿지만, 실제로는 앞선 작업이 안 끝났으면 언제 시작될지 알 수 없습니다. 사용자의 정신 모델과 시스템의 실제 동작이 어긋나 있는 상태이고, 코드 문제가 아니라 설계와 제품 사이의 문제입니다.

## 성과

네트워크가 제한된 폐쇄망 환경에서 Docker 기반으로 관제 시스템과 로봇 측 구성을 배포할 수 있는지, 그리고 중앙–로봇–클라이언트로 이어지는 통신 구조가 성립하는지를 검증하는 것이 PoC의 목표였습니다. 스케줄 명령 전달, 실시간 위치 표시, 카메라 영상 관제가 단일 로봇 기준으로 동작함을 확인했고, 실 운영 전환 시 해결이 필요한 구조적 과제를 도출했습니다.

## 배운 것

자원은 켜는 것과 끄는 것이 한 쌍이어야 합니다. 실무에서 가장 흔한 사고가 "켜는 건 했는데 끄는 걸 안 한" 경우이고, 배터리로 도는 로봇에서는 이게 곧 가동 시간 손실입니다.

그리고 시스템이 기능적으로 동작하는 것과 사용자가 이해한 대로 동작하는 것은 다른 문제입니다. 스케줄 의미론 간극이 그 예입니다.

## 아쉬운 점 · 다시 한다면

- **크론 단일 인스턴스 전제** — 스케줄링이 중앙 서버의 인메모리 크론으로 동작했습니다. PoC라 단일 인스턴스 전제였고, 스케일아웃하면 동일 명령이 로봇에 중복 전달됩니다. 운영 전환 시 Redis 분산 락이나 BullMQ 같은 잡 큐로 단일 실행을 보장해야 합니다.
- **명령 전달 시각과 실행 시각의 간극** — 관제 UI에 예상 실행 시각이나 대기 상태를 노출하는 처리가 필요합니다.
- **트랜스코딩 CPU 확장** — 로봇 대수가 늘면 변환 부하가 선형으로 증가합니다.
- **다중 시청자 팬아웃 / 백프레셔 정책 부재** — 클라이언트 수신이 느릴 때 서버 버퍼가 누적되는 구조라 프레임 드롭 정책이 필요합니다.

로봇 1대 가정이 감췄던 지점: 연결 관리(로봇별 세션 식별·재연결) / 영상(중앙 대역폭, 동시 뷰어 팬아웃) / 스케줄(로봇 간 구역 중복) / 배포(fleet 단위 이미지) / 장애(어느 로봇이 죽었는지 감지).
