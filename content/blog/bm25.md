## 1. BM25란?

**BM25(Best Matching 25)**는 질문에 들어 있는 단어가 문서에 얼마나, 어떻게 등장하는지를 보고 문서에 점수를 매기는 키워드 검색 랭킹 함수입니다. 1990년대 런던 시티 대학교의 Okapi 검색 시스템 연구(Stephen Robertson 등)에서 나왔고, 그래서 **Okapi BM25**라고도 부릅니다.

```text
질문: "연차 이월 규정"
          │
          ▼  단어로 쪼갠다
   [연차] [이월] [규정]
          │
          ▼  각 단어가 등장하는 문서를 찾고 점수를 더한다
┌──────────────────────────────────────────────┐
│ 문서A: "연차 이월은 최대 5일까지..."   12.4   │
│ 문서B: "취업 규정 제3장 연차 휴가..."   8.1   │
│ 문서C: "규정 개정 이력..."             2.3   │
└──────────────────────────────────────────────┘
```

[임베딩 검색](/blog/embedding)이 "뜻이 비슷한 문서"를 찾는다면, BM25는 "질문의 단어가 중요하게 들어 있는 문서"를 찾습니다. 수십 년 된 방법이지만 지금도 Elasticsearch, OpenSearch, Lucene의 기본 랭킹 함수이고, RAG에서도 여전히 핵심 부품입니다.

BM25의 점수 규칙은 이렇게 요약할 수 있습니다.

> 드문 단어가, 짧은 문서에, 적당히 여러 번 나오면 점수가 높다.

## 2. 희소 검색과 밀집 검색

### 2-1. 두 종류의 벡터

검색 방식은 문서를 어떤 벡터로 표현하느냐에 따라 크게 둘로 나뉩니다.

```text
희소 벡터 (Sparse) — BM25, TF-IDF
  어휘 사전 크기만큼의 차원 (수만~수십만), 대부분 0
  [0, 0, 0, 2, 0, 0, ..., 0, 1, 0, 0, ..., 0]
             ↑ "연차"           ↑ "이월"
  → 어떤 단어가 들어 있는지 그대로 보인다

밀집 벡터 (Dense) — 임베딩
  수백~수천 차원, 거의 모든 값이 0이 아님
  [0.021, -0.113, 0.087, ..., 0.004]
  → 각 차원이 무슨 뜻인지 사람이 읽을 수 없다
```

| 구분 | 희소 검색 (BM25) | 밀집 검색 (임베딩) |
|---|---|---|
| 일치 기준 | 단어(토큰)가 같아야 한다 | 의미가 비슷하면 된다 |
| 학습 | 필요 없음 (통계만 계산) | 임베딩 모델 필요 |
| 설명 가능성 | 높음 (어떤 단어로 맞았는지 보임) | 낮음 |
| 고유명사, 코드 | 강하다 | 약하다 |
| 동의어, 바꿔 말하기 | 약하다 | 강하다 |
| 인프라 | 역색인 (검색 엔진) | 벡터 인덱스 (벡터 DB) |

### 2-2. 임베딩이 있는데 왜 아직 BM25를 쓸까?

```text
질문: "ERR_CONN_4021 에러 해결법"

임베딩 검색 결과:
  1. "네트워크 연결 오류가 발생하면 방화벽을..."   (뜻은 비슷하지만 다른 에러)
  2. "에러 코드 목록 및 일반적인 해결 방법..."

BM25 검색 결과:
  1. "ERR_CONN_4021: 프록시 인증서 만료 시 발생. 해결: ..."  ← 정답
```

사용자가 정확한 용어로 검색하는 경우가 생각보다 많습니다. 에러 코드, 제품 모델명, 법 조항 번호, 사람 이름, 사내 프로젝트 코드명 같은 것들입니다. 이런 단어는 임베딩 모델이 학습 중에 본 적이 없거나, 비슷한 다른 단어와 뭉뚱그려 표현하기 쉽습니다. BM25는 글자가 일치하는지만 보기 때문에 이런 경우에 정확합니다.

그래서 실무 RAG에서는 BM25와 임베딩 검색을 함께 쓰는 [하이브리드 검색](/blog/hybrid-search)이 흔합니다. 하이브리드 검색은 별도 노트에서 다룹니다.

## 3. 역색인 (Inverted Index)

BM25가 빠른 이유는 **역색인** 덕분입니다.

### 3-1. 정방향 vs 역방향

```text
정방향 색인 (문서 → 단어)
  문서1: [연차, 이월, 최대, 5일]
  문서2: [취업, 규정, 연차, 휴가]
  문서3: [규정, 개정, 이력]

역색인 (단어 → 문서)
  연차 → [문서1(1회), 문서2(1회)]
  이월 → [문서1(1회)]
  규정 → [문서2(1회), 문서3(1회)]
  개정 → [문서3(1회)]
  ...
```

책 뒤에 있는 **찾아보기(색인)**와 같습니다. "연차"라는 단어가 어느 페이지에 나오는지 바로 알 수 있으니 책 전체를 넘겨 볼 필요가 없습니다.

### 3-2. 검색 흐름

```text
질문 "연차 이월"
  │
  ├─ "연차" 목록 조회 → {문서1, 문서2}
  ├─ "이월" 목록 조회 → {문서1}
  │
  ▼
후보 = {문서1, 문서2}   ← 질문 단어가 하나도 없는 문서는 아예 보지 않는다
  │
  ▼
후보마다 BM25 점수 계산 → 정렬
```

문서가 수천만 개여도, 질문 단어가 들어 있는 문서만 보면 되므로 빠릅니다. 역색인에는 보통 단어별 **등장 횟수(TF)**, **등장한 문서 수(DF)**, 문서 길이 같은 통계도 함께 저장해서 점수 계산에 씁니다.

## 4. TF-IDF에서 BM25로

BM25를 이해하려면 그 이전 방식인 TF-IDF부터 보는 게 좋습니다.

### 4-1. TF (Term Frequency): 많이 나오면 중요하다

문서 안에서 단어가 **많이 나올수록** 그 문서는 그 단어와 관련이 깊다고 봅니다.

```text
문서A: "연차 이월 ... 연차 사용 ... 연차 신청"   → "연차" TF = 3
문서B: "... 연차 ..."                           → "연차" TF = 1
```

### 4-2. IDF (Inverse Document Frequency): 드문 단어가 중요하다

"규정", "합니다", "및" 같은 단어는 거의 모든 문서에 나옵니다. 이런 단어가 일치하는 것은 별 의미가 없습니다. 반대로 "이월"처럼 **소수 문서에만 나오는 단어**가 일치하면 강한 신호입니다.

```text
IDF(단어) = log(전체 문서 수 / 그 단어가 나온 문서 수)

전체 1000개 문서 중
  "이월"이 10개 문서에 등장   → log(1000/10)  = 4.6  (드물다 → 중요)
  "규정"이 900개 문서에 등장  → log(1000/900) = 0.1  (흔하다 → 거의 무의미)
```

### 4-3. TF-IDF

```text
TF-IDF 점수 = Σ (질문의 각 단어에 대해) TF × IDF
```

직관은 좋지만 두 가지 문제가 있습니다.

| 문제 | 예 |
|---|---|
| TF가 끝없이 커진다 | "연차"가 100번 나오는 문서가 10번 나오는 문서보다 10배 관련 있을까? 아니다. 그냥 길거나, 같은 말을 반복했을 뿐이다 |
| 긴 문서가 유리하다 | 300쪽 규정집은 거의 모든 단어를 여러 번 포함하므로 어떤 질문에든 점수가 높게 나온다 |

BM25는 이 두 문제를 **포화(saturation)**와 **길이 정규화(length normalization)**로 해결합니다.

## 5. BM25 수식 직관

### 5-1. 수식

```text
                          f(q, D) × (k1 + 1)
score(D, Q) = Σ IDF(q) × ─────────────────────────────────────
             q∈Q          f(q, D) + k1 × (1 - b + b × |D| / avgdl)

  f(q, D) : 문서 D에서 단어 q의 등장 횟수 (TF)
  |D|     : 문서 D의 길이 (단어 수)
  avgdl   : 전체 문서의 평균 길이
  k1      : TF 포화 정도를 조절 (보통 1.2 ~ 2.0)
  b       : 길이 정규화 강도 (0 ~ 1, 보통 0.75)
```

IDF는 구현마다 조금씩 다르지만, Lucene(Elasticsearch, OpenSearch)은 다음 형태를 씁니다.

```text
IDF(q) = ln(1 + (N - n(q) + 0.5) / (n(q) + 0.5))

  N    : 전체 문서 수
  n(q) : 단어 q가 등장한 문서 수
```

수식이 복잡해 보이지만 세 부분으로 나눠 보면 단순합니다.

```text
점수 = (단어가 얼마나 드문가) × (문서에 얼마나 나오는가, 단 상한 있음) × (문서 길이 보정)
          IDF                       TF 포화 (k1)                         길이 정규화 (b)
```

### 5-2. IDF: 드문 단어일수록 큰 가중치

N = 1000일 때 Lucene 방식 IDF를 계산해 보면 다음과 같습니다.

| 단어가 등장한 문서 수 | IDF | 해석 |
|---|---|---|
| 1 | 약 6.50 | 매우 드물다 → 일치하면 강한 신호 |
| 10 | 약 4.55 | 드물다 |
| 500 | 약 0.69 | 흔하다 |
| 990 | 약 0.01 | 거의 모든 문서에 있다 → 무의미 |

`+1`을 넣은 덕분에 IDF가 음수가 되지 않습니다. 원래 BM25 IDF 공식은 절반 넘는 문서에 나오는 단어에서 음수가 나올 수 있어서, 구현마다 이걸 처리하는 방식이 다릅니다.

### 5-3. k1: TF 포화 (많이 나와도 점수에 상한이 있다)

길이 보정을 잠시 빼고(|D| = avgdl), k1 = 1.2로 TF 부분만 계산해 보면 이렇습니다.

```text
TF 부분 = f × (k1 + 1) / (f + k1)

 f(등장 횟수)   TF 부분     TF-IDF였다면
     1          1.00          1
     2          1.38          2
     5          1.77          5
    10          1.96         10
   100          2.17        100
     ∞          2.20 (= k1+1)
```

```text
TF 부분
 2.2 ┤ - - - - - - - - - - - - - - - - - - -  상한 (k1 + 1)
     │            ●──────●────────────●
 1.5 ┤      ●
     │   ●
 1.0 ┤ ●
     └──┬──┬─────┬──────┬──────────────┬──── 등장 횟수
        1  2     5      10            100
```

처음 몇 번 등장할 때는 점수가 빠르게 오르지만 곧 **포화**됩니다. "연차"가 100번 나와도 10번 나온 문서보다 크게 유리하지 않습니다.

| k1 | 효과 |
|---|---|
| 0 | 등장 횟수 무시. 나왔는지 안 나왔는지만 본다 |
| 작게 (예: 0.5) | 빨리 포화된다. 한 번만 나와도 충분하다고 본다 |
| 크게 (예: 3) | 천천히 포화된다. 여러 번 나올수록 계속 유리하다 |

### 5-4. b: 문서 길이 정규화

같은 단어가 1번 나왔더라도, 짧은 문서에서 1번은 긴 문서에서 1번보다 의미가 큽니다. 짧은 공지문에 "이월"이 나왔다면 그 공지는 이월에 관한 글일 가능성이 높지만, 300쪽 규정집 어딘가에 한 번 나온 건 별 의미가 없을 수 있습니다.

k1 = 1.2, b = 0.75, 등장 횟수 1회일 때 TF 부분은 다음과 같습니다.

| 문서 길이 | 분모의 k1 부분 | TF 부분 |
|---|---|---|
| 평균의 절반 | 1.2 × (0.25 + 0.375) = 0.75 | 2.2 / 1.75 ≈ 1.26 |
| 평균 | 1.2 × 1.0 = 1.2 | 2.2 / 2.2 = 1.00 |
| 평균의 2배 | 1.2 × (0.25 + 1.5) = 2.1 | 2.2 / 3.1 ≈ 0.71 |

| b | 효과 |
|---|---|
| 0 | 길이 보정 없음. 긴 문서가 유리할 수 있다 |
| 0.75 | 일반적인 기본값 |
| 1 | 길이에 정비례하게 보정. 짧은 문서가 강하게 유리하다 |

문서 길이가 비슷비슷하면(예: 같은 크기로 자른 청크) b의 영향이 작아집니다. RAG에서 문서를 일정 크기로 청킹해서 넣는 경우가 여기에 해당해서, 길이 정규화의 역할이 줄어듭니다.

### 5-5. 기본값

| 구현 | k1 | b |
|---|---|---|
| Elasticsearch / OpenSearch (Lucene) | 1.2 | 0.75 |
| Python `rank_bm25`의 `BM25Okapi` | 1.5 | 0.75 |

대부분 기본값으로 시작해도 무난합니다. 바꾸려면 평가 데이터셋을 만들어 놓고 비교해야 합니다.

## 6. Python으로 BM25 써 보기

### 6-1. rank_bm25

```python
from rank_bm25 import BM25Okapi

docs = [
    "연차 이월은 최대 5일까지 가능합니다",
    "취업 규정 제3장 연차 휴가 사용 기준",
    "규정 개정 이력 및 시행일",
    "ERR_CONN_4021 오류는 프록시 인증서 만료 시 발생합니다",
]

tokenized = [d.split() for d in docs]   # 일단 공백으로 자른다 (문제는 7장)
bm25 = BM25Okapi(tokenized)

query = "연차 이월".split()
print(bm25.get_scores(query))
print(bm25.get_top_n(query, docs, n=2))
```

`get_scores`는 모든 문서의 점수를, `get_top_n`은 상위 n개 문서를 돌려줍니다. `rank_bm25`는 역색인 없이 모든 문서를 계산하는 단순 구현이라 학습과 프로토타입용으로 적합합니다. 대량 문서에는 검색 엔진을 씁니다 (8장).

### 6-2. 공백 분리의 함정

위 예제에서 `"연차 이월은 최대..."`를 공백으로 자르면 토큰이 `"이월은"`이 됩니다. 질문의 `"이월"`과 글자가 다르므로 일치하지 않습니다.

```text
문서 토큰:  [연차] [이월은] [최대] [5일까지] [가능합니다]
질문 토큰:  [연차] [이월]
일치:        연차만 ✓   이월 ✗
```

영어는 공백 분리만으로도 어느 정도 되지만, 한국어에서는 이 문제가 심각합니다.

## 7. 한국어의 형태소 분석 이슈

### 7-1. 왜 한국어는 어려운가

한국어는 **교착어**라서 단어(어간) 뒤에 조사와 어미가 붙어 형태가 계속 바뀝니다.

```text
"이월"  →  이월은, 이월이, 이월을, 이월된, 이월하면, 이월할 수 있는지
"신청"  →  신청서, 신청하려면, 신청했는데, 신청합니다
```

공백으로 자르면 이것들이 모두 다른 토큰이 됩니다. BM25는 글자가 일치해야 점수를 주므로 검색이 거의 안 됩니다.

### 7-2. 해결 방법

| 방법 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 형태소 분석 | 어간과 조사, 어미를 분리한다 | 정확하다, 품사로 불용어 제거 가능 | 사전에 없는 신조어, 고유명사를 잘못 자를 수 있다 |
| n-gram | 글자를 2~3글자씩 겹쳐 자른다 | 사전이 필요 없다, 신조어에 강하다 | 색인이 커지고, 엉뚱한 일치가 늘어난다 |
| 둘 다 | 필드를 나눠 둘 다 색인한다 | 서로 보완한다 | 복잡도와 저장 공간 증가 |

```text
형태소 분석:  "이월은 최대 5일까지"  →  [이월] [최대] [5] [일]
bigram:      "이월은"              →  [이월] [월은]
```

### 7-3. 한국어 형태소 분석기

| 도구 | 환경 | 비고 |
|---|---|---|
| Nori | Elasticsearch / OpenSearch 플러그인 | Lucene 기반, mecab-ko-dic 사전 사용 |
| Kiwi (`kiwipiepy`) | Python | 설치가 쉽고 빠른 편 |
| KoNLPy (Okt, Mecab 등) | Python | 여러 분석기를 감싼 래퍼, 일부는 Java 필요 |

### 7-4. Kiwi로 토큰화하고 BM25에 넣기

```python
from kiwipiepy import Kiwi
from rank_bm25 import BM25Okapi

kiwi = Kiwi()
KEEP = ("NN", "VV", "VA", "SL", "SN", "SH", "XR")  # 명사, 동사, 형용사, 외국어, 숫자 등

def tokenize(text):
    return [t.form for t in kiwi.tokenize(text) if t.tag.startswith(KEEP)]

docs = [
    "연차 이월은 최대 5일까지 가능합니다",
    "취업 규정 제3장 연차 휴가 사용 기준",
    "규정 개정 이력 및 시행일",
]
bm25 = BM25Okapi([tokenize(d) for d in docs])

print(tokenize("연차를 이월할 수 있나요?"))
print(bm25.get_top_n(tokenize("연차를 이월할 수 있나요?"), docs, n=1))
```

조사, 어미를 버리고 의미 있는 형태소만 남기면 "이월은"과 "이월할"이 모두 "이월"로 맞춰집니다. 어떤 품사를 남길지는 데이터에 따라 조정합니다. **문서와 질문은 반드시 같은 토크나이저**를 써야 합니다.

### 7-5. 사용자 사전

형태소 분석기는 사전에 없는 단어를 잘못 자를 수 있습니다.

```text
"클로드코드"  →  [클로드] [코드]   (붙어 있어야 하는 제품명이 쪼개짐)
"연말정산"    →  [연말] [정산]     (분석기에 따라 다름)
```

사내 용어, 제품명, 프로젝트 코드명이 많다면 **사용자 사전**에 등록해야 합니다. Nori, Kiwi 모두 사용자 사전을 지원합니다.

### 7-6. 동의어 사전

BM25의 가장 큰 약점은 동의어입니다. "연차"로 검색하면 "휴가"만 쓰인 문서는 찾지 못합니다. 검색 엔진에서는 **동의어 사전(synonym filter)**으로 일부 보완할 수 있습니다.

```text
연차, 휴가, 연가
퇴사, 퇴직, 사직
```

다만 사람이 관리해야 하고, 모든 바꿔 말하기를 다 등록할 수는 없습니다. 이 한계를 근본적으로 메우는 것이 임베딩 검색입니다.

## 8. Elasticsearch / OpenSearch

실무에서 BM25를 대규모로 쓸 때는 보통 직접 구현하지 않고 **검색 엔진**을 씁니다. Elasticsearch와 OpenSearch(Elasticsearch에서 포크된 오픈소스 프로젝트)는 둘 다 Lucene 기반이고, 기본 랭킹 함수가 BM25입니다.

### 8-1. Nori 분석기로 인덱스 만들기

```json
PUT /policies
{
  "settings": {
    "analysis": {
      "analyzer": {
        "korean": {
          "type": "custom",
          "tokenizer": "nori_tokenizer",
          "filter": ["nori_part_of_speech", "lowercase"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "title":   { "type": "text", "analyzer": "korean" },
      "content": { "type": "text", "analyzer": "korean" },
      "dept":    { "type": "keyword" }
    }
  }
}
```

Nori는 별도 플러그인(`analysis-nori`)으로 설치합니다. `nori_part_of_speech` 필터는 조사, 어미 같은 품사를 제거합니다. `dept`처럼 정확히 일치해야 하는 필드는 분석하지 않는 `keyword` 타입으로 둡니다.

### 8-2. 검색하기

```python
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")

resp = es.search(index="policies", query={
    "bool": {
        "must": {
            "multi_match": {
                "query": "연차 이월 규정",
                "fields": ["title^2", "content"],   # 제목 일치에 2배 가중치
            }
        },
        "filter": {"term": {"dept": "hr"}},
    }
}, size=5)

for hit in resp["hits"]["hits"]:
    print(hit["_score"], hit["_source"]["title"])
```

`filter` 절은 점수에 영향을 주지 않고 조건만 겁니다. 역색인 위에서 동작하므로 벡터 DB의 필터링 문제(결과가 비는 현상)가 상대적으로 덜합니다.

### 8-3. 검색 엔진이 주는 것

| 기능 | 설명 |
|---|---|
| 역색인 | 수천만 문서에서도 빠른 검색 |
| 분석기 | 형태소 분석, 동의어, 불용어, n-gram |
| 필드 가중치 | 제목 일치를 본문 일치보다 중요하게 |
| 구문 검색 | `"연차 이월"`을 붙어 있는 순서 그대로 찾기 |
| 필터, 집계 | 부서, 날짜, 권한 조건 |
| 벡터 검색 | 최근 버전은 kNN 검색도 지원해 하이브리드 검색 가능 |
| 점수 설명 | `explain` API로 어떤 단어가 몇 점을 줬는지 확인 |

## 9. RAG에서 BM25의 위치

### 9-1. 임베딩 없는 RAG의 출발점

BM25만으로도 RAG를 만들 수 있습니다.

```text
질문 ──> 형태소 분석 ──> BM25 검색 (상위 k개) ──> LLM에 문서와 함께 전달 ──> 답변
```

| 장점 | 설명 |
|---|---|
| 임베딩 모델이 필요 없다 | GPU, 임베딩 API 비용 없음 |
| 이미 있는 인프라를 쓴다 | 사내에 Elasticsearch가 있다면 바로 시작 |
| 재색인이 싸다 | 문서를 바꿔도 임베딩을 다시 만들 필요가 없다 |
| 디버깅이 쉽다 | 왜 이 문서가 나왔는지 단어 단위로 보인다 |

벡터 없이 검색하는 RAG(Vectorless RAG)를 이야기할 때 가장 먼저 떠올릴 수 있는 출발점이 BM25입니다. 그 위에 문서 구조 탐색이나 LLM의 판단을 더하는 방식은 별도 노트에서 다룹니다.

### 9-2. 질문 변환으로 약점 보완

BM25는 사용자의 구어체 질문에 약합니다. "연차를 내년으로 넘길 수 있나요?"에는 "이월"이라는 단어가 없습니다. LLM으로 질문을 검색용 키워드로 바꾸거나 동의어를 덧붙이면 BM25 성능이 크게 오를 수 있습니다.

```text
원래 질문:  "연차를 내년으로 넘길 수 있나요?"
변환 질문:  "연차 이월 휴가 이월 규정 다음 해"
```

이런 기법은 [질문 변환(Query Transformation)](/blog/rag-query-transformation) 노트에서 다룹니다.

### 9-3. 하이브리드 검색의 한 축

```text
             ┌──> BM25 (정확한 단어)   ──┐
질문 ────────┤                          ├──> 결과 합치기 ──> 리랭킹 ──> LLM
             └──> 임베딩 (비슷한 의미)  ──┘
```

두 방식의 약점이 서로 반대라서 함께 쓰면 보완이 잘 됩니다. 자세한 결합 방법은 하이브리드 검색 노트에서 다룹니다.

## 10. 장점과 단점

| 장점 | 설명 |
|---|---|
| 정확한 용어에 강하다 | 에러 코드, 모델명, 조항 번호, 사람 이름, 고유명사 |
| 학습이 필요 없다 | 문서 통계만으로 동작한다 |
| 빠르고 가볍다 | 역색인으로 대규모에서도 빠르고, GPU가 필요 없다 |
| 설명 가능하다 | 어떤 단어가 몇 점을 줬는지 알 수 있다 |
| 도메인 이동에 강하다 | 처음 보는 분야의 문서도 단어만 맞으면 찾는다 |
| 성숙한 생태계 | Elasticsearch, OpenSearch, Lucene |

| 단점 | 설명 |
|---|---|
| 동의어에 약하다 | "연차" ↔ "휴가"를 모른다 (동의어 사전으로 일부 보완) |
| 바꿔 말하기에 약하다 | "내년으로 넘기다" ↔ "이월" |
| 어순, 문맥을 모른다 | "A가 B를 고소" vs "B가 A를 고소"를 구분하지 못한다 |
| 부정을 모른다 | "환불 가능" vs "환불 불가"에 같은 단어가 겹친다 |
| 한국어는 전처리가 필수 | 형태소 분석기, 사용자 사전 관리가 필요하다 |
| 다국어 검색 불가 | 한국어 질문으로 영어 문서를 찾지 못한다 |

### 10-1. BM25만으로 충분한 경우

- 사용자가 정확한 용어로 검색하는 경우가 대부분이다 (개발 문서, 에러 코드, 법령 검색)
- 이미 Elasticsearch, OpenSearch를 운영하고 있다
- 임베딩 모델을 도입할 비용이나 보안 여건이 안 된다
- 일단 빠르게 기준선(baseline)을 만들고 싶다

### 10-2. BM25만으로 부족한 경우

- 사용자가 자연어 질문, 구어체로 묻는다
- 같은 개념을 여러 표현으로 쓰는 문서가 많다
- 다국어 문서를 검색해야 한다

이런 경우에는 임베딩 검색이나 하이브리드 검색을 함께 검토합니다. 그래도 BM25를 기준선으로 먼저 측정해 두면, 임베딩 검색이 BM25보다 정말 나은지 비교할 수 있습니다.

## 11. 핵심 정리

> BM25는 질문의 단어가 문서에 어떻게 등장하는지로 점수를 매기는 키워드(희소) 검색 랭킹 함수로, Elasticsearch와 OpenSearch의 기본값이다. 역색인으로 질문 단어가 들어 있는 문서만 빠르게 골라내고, IDF로 드문 단어에 큰 가중치를 주며, k1로 등장 횟수의 효과에 상한을 두고, b로 긴 문서의 이점을 깎는다. 한국어는 조사와 어미 때문에 공백 분리로는 검색이 거의 안 되므로 Nori나 Kiwi 같은 형태소 분석기와 사용자 사전이 필수다. 에러 코드, 고유명사처럼 정확한 용어에 강하고 동의어와 바꿔 말하기에 약해서, 임베딩 검색과 약점이 정반대다. 그래서 BM25는 임베딩 없는 RAG의 출발점이자, 하이브리드 검색의 한 축이자, 임베딩 검색을 평가할 때의 기준선이 된다.
