# RAG PoC Harness

`samples/`의 실제 콘텐츠로 청킹 경계와 검색 품질을 측정한다. 의존성 없이 표준 라이브러리만 쓴다.

```bash
python3 poc/rag_eval.py chunks     # 청킹 측정 (API 키 불필요)
python3 poc/rag_eval.py selftest   # 자체 검증 (API 키 불필요)
python3 poc/rag_eval.py search     # 임베딩 + 검색 평가 (OPENAI_API_KEY 필요)
```

Spring AI가 아니라 Python 스크립트인 이유는 이 코드가 제품이 아니라 측정 도구이기 때문이다.
여기서 얻는 결론(청크 크기, 경계 규칙, 모델 적합성)은 언어와 무관하게 이전된다.
제품 구현은 RAG_DESIGN대로 Spring Boot에서 한다.

## 측정 결과 — 2026-09-09

문서 6건 (공개 5 / 비공개 1), 본문 합계 약 13,400자.

| 전략 | 청크 수 | 최소 | 중앙 | 최대 | 200자 미만 | 1200자 초과 |
|---|---|---|---|---|---|---|
| A: 섹션 = 청크 | 46 | 88 | 268 | 647 | 11 | 0 |
| B: 짧은 섹션 병합 | 35 | 205 | 367 | 821 | 0 | 0 |

**가장 긴 섹션이 647자였다.** 섹션이 길어서 쪼개야 한다는 기존 가정은 이 콘텐츠 규모에서 틀렸다.
실제 문제는 반대였다. "정리", "시작", "개요" 같은 짧은 섹션 11개가 그대로 청크가 되면 검색 노이즈가 된다.

병합 후 35청크 중 **9개가 두 개 이상의 섹션에 걸친다**(`주의할 점 + 정리`, `시작 + HLS를 뺀 이유`).
따라서 `document_chunk.section_title`을 단일 컬럼으로 두면 출처를 정확히 표시할 수 없다.
DATA_MODEL을 `section_titles text[]`로 수정했다.

### 하네스가 함께 검증하는 것

- 관리자 전용 필드(`admin_note`, `open_questions`, `sample_note`)가 색인 본문에 섞이지 않는다 — DATA_MODEL 공백 5번
- 추천 질문 블록(`:::questions`)이 색인 본문에서 제거된다 — 근거가 아니라 UI 요소이므로
- 비공개 문서(`offline-first-boundary`)가 검색 대상에서 제외된다 — ADR-0005 결정 3, RAG-007

`selftest`가 이 세 가지를 assert로 확인한다.

## 검색 평가 결과 — 2026-09-09

공개 문서 5건 / 35청크 / 질문 7개, `text-embedding-3-small`(실측 차원 1536), 상위 5.

| 질문 | 기대 출처 | 상위 1건 | 결과 |
|---|---|---|---|
| React Native 프로젝트 경험 | viora | 0.372 | 포함 |
| AI 관련 프로젝트 경험 | viora | 0.425 | 포함 |
| 폐쇄망 실시간 영상 전송 | yujin-robot, websocket-binary-video | 0.518 | 포함 |
| 브라우저 USB 직접 통신 | syncmaster, web-serial-usb | 0.439 | 포함 |
| 오프라인 동기화 충돌 | syncmaster | 0.520 | 포함 |
| WebRTC 대신 WebSocket | websocket-binary-video, yujin-robot | 0.678 | 포함 |
| OAuth 트러블슈팅 | 없음 | 0.342 | 근거 부족 기대 |

**기대 출처 포함 7/7.**

### 비공개 필터가 실제로 동작한다

비공개 문서 `offline-first-boundary`는 7개 질문의 상위 결과에 한 번도 나오지 않았다.
"오프라인 우선 앱에서 동기화 충돌을 어떻게 처리했나요?"는 그 비공개 글의 제목과 거의 같은 질문인데도
공개 원본인 `syncmaster`가 0.520으로 최상위였다. ADR-0005의 조회 시점 필터 검증(RAG-007) 통과.

### 임계값으로는 근거 부족을 판정할 수 없다

- 근거 있는 질문의 최저 상위 점수: **0.372** (React Native)
- 근거 없는 질문의 상위 점수: **0.342** (OAuth)
- 간격 **0.030**

이 폭에서는 고정 컷오프가 정상 질문을 잘라내거나 없는 근거를 통과시킨다.
OAuth 질문의 상위 3건이 전부 각 프로젝트의 "트러블슈팅" 섹션이었다는 점이 원인을 보여준다.
질문의 "트러블슈팅"이라는 단어가 섹션 제목과 매칭된 것이지 OAuth 내용이 있어서가 아니다.
근거 충분 여부는 생성 단계에서 판단해야 한다(ADR-0006 결정 3).

### 기술명 조회가 가장 약하다

"React Native"가 0.372로 최저였다. 해당 기술명이 긴 청크 안에 한 번 등장해 벡터 유사도가 희석된다.
기술명 조회는 포트폴리오 챗봇의 주요 패턴이라 Hybrid search 검토 대상으로 올렸다.

## 아직 측정하지 못한 것

- 전략 A(섹션 = 청크)와 B(병합)의 검색 정확도 차이. B로만 측정했다.
- pgvector HNSW의 근사 검색 회수율. 메모리 코사인으로 측정해 인덱스 영향이 빠져 있다.
- 생성 모델 품질. 검색까지만 측정했고 답변 생성은 실행하지 않았다.
- 콘텐츠가 늘어난 뒤의 점수 분포. 현재 표본은 문서 5건, 질문 7개다.

## 한계

- 토큰이 아니라 문자 수로 잰다. 경계 비교에는 충분하지만 절대 토큰 예산 확인에는 tiktoken이 필요하다.
- pgvector를 쓰지 않고 메모리에서 코사인을 계산한다. 청크 수십 개 규모에서 인덱스는 측정에 영향을 주지 않는다. HNSW 파라미터 검증은 실제 DB가 생긴 뒤에 한다.
- 블로그 3편이 AI 초안이라 문체가 균질하다. 실제 원고로 교체하면 청크 길이 분포가 달라질 수 있다.
