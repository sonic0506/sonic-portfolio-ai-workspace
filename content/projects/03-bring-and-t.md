## 프로젝트 개요

브링앤티는 기존 차량의 스마트키를 스마트폰과 연동해 디지털키처럼 사용할 수 있도록 지원하는 현대모비스의 차량용 디지털키 서비스입니다. 사용자는 모바일 앱을 통해 차량 문을 열고 잠그거나 오토도어 기능을 이용할 수 있으며, 디지털키 공유를 기반으로 차량 관리 서비스까지 연계할 수 있습니다.

별도의 차량 개조 없이 기존 스마트키와 전용 디바이스를 활용해 디지털키 기능을 제공함으로써, 디지털키가 기본 탑재되지 않은 차량에서도 보다 편리한 차량 이용 경험을 제공합니다.

이 서비스를 운영하기 위한 관리자 웹을 새로 만들었습니다. 앱에서 이뤄지는 디지털키 등록·공유와 차량 이용 현황을 운영자가 확인하고, 전용 디바이스의 생산부터 CS까지 한곳에서 관리합니다.

## 주요 성과

- **FSD 도입과 개발 규칙 정리**: 기능·도메인 단위로 책임을 나누는 FSD(Feature-Sliced Design)를 팀 공통 개발 규칙으로 정했습니다. 화면이 늘어나도 같은 구조로 코드를 추가하면 돼서 유지보수와 확장이 쉬워졌습니다.
- **공통 컴포넌트와 반복 로직 모듈화**: 디자인 시스템에 맞춰 공통 UI 컴포넌트와 테이블·필터처럼 반복되는 로직을 모듈로 분리하고, 페이지 유형별로 재사용할 수 있는 구조를 만들었습니다. 새 페이지를 만들 때 같은 코드를 다시 짜는 일이 줄었습니다.
- **페이지 유형별 AI 개발 방식 적용**: FSD 구조와 페이지 구성 요소를 기준으로, 형태가 정해진 화면은 AI로 만들었습니다. 반복 작업이 줄어 개발 속도가 빨라졌습니다.
- **개발 기준 공유와 작업 관리**: PL로서 공통 컴포넌트 사용법과 페이지 구현 규칙을 정해 공유했고, 이를 기준으로 팀원별 작업 분배와 일정 조율을 맡았습니다. 덕분에 여러 개발자가 같은 구조와 기준으로 작업할 수 있었습니다.
- **S3·CloudFront 배포 자동화**: 현업에서 전달받은 인프라 환경에 맞춰 GitHub Actions로 S3 배포와 CloudFront 캐시 무효화를 자동화해 수동 배포 절차를 줄였습니다.

## 좋았던 점

### 반복 구현 시간을 줄이고 검수에 집중할 수 있었던 점

예전에는 복사·붙여넣기로 만들던 반복 화면을 AI에 맡기니 개발 시간이 많이 줄었다고 느꼈습니다. 코드 순서나 규칙을 더 잘 지킬 때도 있었습니다.

### 공통 기준을 사람과 AI의 작업에 함께 사용한 점

컨벤션, 유형별 예시 페이지, 공통 컴포넌트를 먼저 만들어 팀에 공유했고, 같은 자료를 AI 작업 기준으로도 썼습니다. 페이지마다 다른 필터·테이블 필드는 디자인 이미지로 전달했고, 기존 유형에 없는 컴포넌트는 따로 개발 업무로 나눴습니다.

구현 전에는 요구사항과 맞는지를, 구현 후에는 코드 규칙과 실제 화면 동작을 확인하도록 단계를 나눴습니다.

## 아쉬운 점

### FSD를 도입한 뒤에도 분류 기준을 구체화해야 했던 점

도메인과 UI를 함께 생각하는 방식에 익숙해지는 데 시간이 걸렸습니다. 처음에는 도메인이 들어간 재사용 컴포넌트를 모두 `widgets`로 분류하다 보니 단순 컨테이너까지 그곳에 쌓였습니다. 나중에 단순 컨테이너는 해당 슬라이스의 `ui`에 두도록 규칙을 바꿨습니다.

패턴을 고른 뒤에도 프로젝트에서 쓰는 컴포넌트의 역할에 맞춰 분류 기준을 계속 다듬어야 했습니다.

### 행위 중심 이름만으로는 도메인별 탐색이 충분하지 않았던 점

`create-admin`, `update-user`처럼 행위가 앞에 오는 슬라이스 이름은 생성·수정별로는 정렬되지만 도메인이 뒤섞였습니다. 중복 확인처럼 CUD로 설명하기 어려운 기능도 있었습니다. 그래서 도메인 아래에 개별 기능을 묶는 2계층 구조를 개선 방향으로 정리했습니다.

### 예시 페이지에 의존한 AI 작업 기준을 더 세분화하고 싶은 점

이번에는 유형별 예시 페이지를 기준으로 AI 개발을 했습니다. 다음에는 라이브러리별 사용 규칙과 공통 컨벤션을 더 잘게 나눠서, 페이지 예시 없이도 필요한 규칙을 찾아 적용하는 방식을 해 보려고 합니다.
