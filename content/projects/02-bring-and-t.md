## 프로젝트 개요

현대모비스 디지털키 서비스인 브링앤티를 운영하기 위한 관리자 웹을 새로 만들었습니다. 디지털키 사용자·앱 이용자 관리, 서비스 운영 로그 조회, 차량 관리 기능을 맡았습니다.

개발자 2명 중 PL로서 기술 선정, 개발 방식 설계, 업무 분배를 맡았습니다. 예전에 Atomic Design을 쓰면서 도메인과 공통 영역을 구분하기 어려웠던 경험이 있어 이번에는 FSD를 도입했습니다. 공통 규칙과 페이지 유형별 예시를 만들어 두고, 반복되는 화면은 AI로 개발했습니다.

| 항목 | 내용 |
|---|---|
| 팀 구성 | 개발 2명 |
| 나의 역할 | PL·관리자 웹 개발, 라이브러리 선정, FSD·컨벤션·예시 페이지·공통 컴포넌트 작성 및 공유, AI 구현 전후 검수, 업무 분배 |

## 주요 성과

- **관리자 웹 신규 구축:** 디지털키 사용자·앱 이용자 관리, 서비스 운영 로그 조회, 차량 관리 등 관리자 기능을 개발했습니다. PL로서 주요 라이브러리를 직접 골랐고, 공통 규칙에 맞춘 개발과 추가 컴포넌트 구현을 나눠 맡겼습니다.
- **도메인과 역할을 기준으로 개발 구조 정리:** FSD를 도입하고 레이어별 책임과 명명 규칙을 컨벤션 문서로 만들어 공유했습니다. 도메인의 조회·표현은 `entities`, 생성·수정·삭제는 `features`, 도메인과 무관한 공용 자원은 `shared`에 두는 것으로 정했습니다.
- **화면 유형별 구현 기준 제공:** 조회·상세·등록/수정 예시 페이지와 필터·테이블 셀 공통 컴포넌트를 직접 만들어 공유했습니다. 필터·셀 유형은 사전 디자인 시스템 작업에서 준비해 둔 구성을 썼습니다.
- **AI 활용 개발 및 검수 절차 적용:** 페이지 유형과 Figma 디자인 이미지를 입력으로 주고, 구현 전에 AI가 뽑아낸 문구·필드 유형을 요구사항과 대조했습니다. 구현 후에는 코드 규칙을 리뷰하고 개발 모드에서 직접 실행하며 수동 QA를 했습니다.
- **FSD 적용 중 컴포넌트 분류 기준 조정:** `widgets`에 단순 컨테이너까지 쌓이는 것을 보고, Dialog·Sheet·Card 등을 감싸기만 하는 컴포넌트는 해당 슬라이스의 `ui`에 두도록 규칙을 바꿨습니다.

## 좋았던 점

### 반복 구현 시간을 줄이고 검수에 집중할 수 있었던 점

예전에는 복사·붙여넣기로 만들던 반복 화면을 AI에 맡기니 개발 시간이 많이 줄었다고 느꼈습니다. 코드 순서나 규칙을 더 잘 지킬 때도 있었습니다. 전후를 측정한 값은 자료에 없어서 몇 퍼센트 줄었다고 말할 수는 없습니다.

### 공통 기준을 사람과 AI의 작업에 함께 사용한 점

컨벤션, 유형별 예시 페이지, 공통 컴포넌트를 먼저 만들어 팀에 공유했고, 같은 자료를 AI 작업 기준으로도 썼습니다. 페이지마다 다른 필터·테이블 필드는 디자인 이미지로 전달했고, 기존 유형에 없는 컴포넌트는 따로 개발 업무로 나눴습니다.

구현 전에는 요구사항과 맞는지를, 구현 후에는 코드 규칙과 실제 화면 동작을 확인하도록 단계를 나눴습니다.

## 아쉬운 점

### FSD를 도입한 뒤에도 분류 기준을 구체화해야 했던 점

도메인과 UI를 함께 생각하는 방식에 익숙해지는 데 시간이 걸렸습니다. 처음에는 도메인이 들어간 재사용 컴포넌트를 모두 `widgets`로 분류하다 보니 단순 컨테이너까지 그곳에 쌓였습니다. 나중에 단순 컨테이너는 해당 슬라이스의 `ui`에 두도록 규칙을 바꿨습니다.

패턴을 고른 뒤에도 프로젝트에서 쓰는 컴포넌트의 역할에 맞춰 분류 기준을 계속 다듬어야 했습니다.

### 행위 중심 이름만으로는 도메인별 탐색이 충분하지 않았던 점

`create-admin`, `update-user`처럼 행위가 앞에 오는 슬라이스 이름은 생성·수정별로는 정렬되지만 도메인이 뒤섞였습니다. 중복 확인처럼 CUD로 설명하기 어려운 기능도 있었습니다. 그래서 도메인 아래에 개별 기능을 묶는 2계층 구조를 개선 방향으로 정리했는데, 실제 소스에 반영됐는지는 지금 자료만으로는 알 수 없습니다.

### 예시 페이지에 의존한 AI 작업 기준을 더 세분화하고 싶은 점

이번에는 유형별 예시 페이지를 기준으로 AI 개발을 했습니다. 다음에는 라이브러리별 사용 규칙과 공통 컨벤션을 더 잘게 나눠서, 페이지 예시 없이도 필요한 규칙을 찾아 적용하는 방식을 해 보려고 했습니다.

관련 에이전트 구성은 이후에 시도한 내용입니다. 브링앤티에서 완료한 기능이나 검증된 자동화 성과로 보면 안 됩니다.
