## 프로젝트 개요

부스트리는 피부과를 중심으로 비급여 의료기관의 운영과 마케팅을 돕는 B2B SaaS 기반 병원 운영 솔루션입니다. 고객 상담·관리와 재방문 관리처럼 병원에서 반복되는 업무를 디지털로 옮기고, 운영에 필요한 정보도 함께 관리할 수 있게 합니다.

서비스의 하나로 병원별 홈페이지와, 그 구성을 관리하는 관리자 페이지를 제공합니다. 저는 초기 MVP 개발에 참여해 병원 관리자 페이지와 병원 홈페이지를 개발했습니다.

관리자 페이지에서는 홈페이지에 노출되는 메뉴와 메뉴별 콘텐츠를 병원이 직접 추가하고 수정할 수 있게 했습니다. 병원 홈페이지는 병원마다 브랜드와 요구사항에 맞춰 UI를 다르게 만들었고, 관리자에서 설정한 메뉴와 콘텐츠가 실제 홈페이지에 반영되도록 연동했습니다.

| 항목 | 내용 |
|---|---|
| 팀 구성 | PM 1명, 디자이너 1명, 백엔드 개발자 1명, 프론트엔드 개발자 2명(본인 포함) |

## 주요 성과

- **병원별 사이트 개발을 위한 공통 기반 구축**: 동료 개발자와 공통 컴포넌트 범위를 정하고, shadcn으로 쓸 부분과 직접 구현할 부분을 나눴습니다. 공통 컴포넌트를 나눠 구현해 seed 저장소에 담았고, 병원별 사이트는 이 저장소를 바탕으로 개발했습니다. 덕분에 UI 구현과 메뉴 설정·API 연동 구조를 사이트마다 다시 만들지 않고 재사용할 수 있었습니다.
- **파트너별 ECS 배포 자동화**: GitHub Actions에서 파트너 명칭을 입력하면 AWS 리소스를 조회해 해당 병원의 ECS를 찾고 Docker 이미지를 배포하도록 했습니다. 프론트엔드 배포에 필요한 AWS 설정을 맡았고, ECS 롤백으로 이전 버전으로 되돌릴 수 있게 했습니다.
- **검색 노출을 고려한 ISR 적용**: 검색엔진이 상품 정보를 읽을 수 있도록 Next.js App Router 환경에 ISR을 적용했습니다. 페이지 소스를 열어 상품 데이터가 실제 HTML에 들어 있는지 직접 확인했습니다.

## 좋았던 점

### SaaS를 초기 MVP 단계부터 만들어 본 점

부스트리에는 초기 MVP 개발 때부터 참여했습니다. 병원이 메뉴와 콘텐츠를 직접 바꾸는 관리자 페이지와, 그 설정을 받아 보여 주는 병원별 홈페이지를 처음부터 만들었습니다.

서비스를 쓰는 병원이 늘면서 사이트마다 반복되던 작업을 seed 저장소로 묶고, 파트너별 배포를 자동화하고, 지점마다 늘어나던 인프라 비용을 줄이는 일이 생겼습니다. 여러 병원이 함께 쓰는 서비스가 고객이 늘 때 어떤 부분부터 바뀌어야 하는지 초기 단계부터 직접 겪어 본 경험이 좋았습니다.

## 아쉬운 점

### 사용량 기준 없이 인프라를 구성한 점

처음에는 지점마다 ALB, ECS 서비스, EC2 인스턴스를 하나씩 두었고, 운영하면서 ALB와 개발 서버 비용이 중복된다는 걸 확인한 뒤에야 구조를 줄였습니다.

병원별 방문자 수 같은 실제 사용량을 먼저 살펴보고, 어느 규모에서 리소스를 나누고 어느 규모에서 합칠지 규칙을 정해 둔 상태로 인프라를 구성해 봤으면 좋았을 것 같습니다.

### 지점별 요구사항 차이를 먼저 분석하지 못한 점

지점마다 UI와 콘텐츠 구성이 달라서 지점별 Next.js 프로젝트를 따로 두었습니다. seed 저장소로 공통 부분을 묶긴 했지만, 지점이 늘면 프로젝트와 배포 대상도 함께 늘어나는 구조였습니다.

지점별 요구사항이 실제로 얼마나 다른지 먼저 분석했다면 다른 선택지도 있었을 것 같습니다. 공통 UI와 데이터 구조로 충분하다면 하나의 Next.js 애플리케이션에서 테넌트별 설정만 분리하는 방향도 고민해 봤으면 좋았겠다는 아쉬움이 남습니다.
