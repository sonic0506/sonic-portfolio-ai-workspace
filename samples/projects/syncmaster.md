## 개요

USB로 직접 연결된 모뎀 디바이스의 설정을 조회·수정하는 웹 기반 관리 도구입니다. 현장 엔지니어가 네트워크가 없는 환경에서도 기기를 다룰 수 있어야 했습니다.

:::questions
- 브라우저에서 USB 기기와 직접 통신하는 게 가능한가요?
- 오프라인 우선 앱에서 동기화 충돌을 어떻게 처리했나요?
:::

## 배경 · 문제

- **네트워크를 전제할 수 없음** — 사용하는 국가와 위치 특성상 망이 제대로 동작하지 않습니다. 현장 투입 전에 필요한 세팅을 마치고, 실제 현장에서는 오프라인 모드로 작업하는 흐름이었습니다.
- **통신 대상이 서버가 아님** — 데이터의 출처가 HTTP API가 아니라 Web Serial로 연결된 물리 디바이스였고, 모든 데이터가 바이너리로 오갔습니다.
- **모델이 계속 늘어남** — 모뎀 모델마다 설정 항목과 바이너리 구조가 달랐습니다. 하드웨어 대응 소프트웨어의 진짜 난이도는 여기 있습니다.

## 역할 · 기여도

웹 클라이언트 전체를 단독 설계·개발했습니다. 오프라인 지원 범위 정의, 바이너리 변환 계층 설계, 서비스 워커 캐싱 전략 모두 포함됩니다.

## 기술 선택 이유

**(a) 오프라인 지원 범위를 기능 단위로 분리**

오프라인에서 허용할 기능을 "서버 없이도 의미가 성립하는 작업"으로 한정했습니다. USB로 연결된 기기의 조회·수정, 이미 받아둔 모뎀 리스트 열람, 로컬에 저장된 기본 설정 적용, 다국어 전환은 오프라인에서 동작하도록 하고, 서버를 통한 등록·수정은 아예 차단했습니다.

오프라인 쓰기를 허용하면 재연결 시점에 서버 상태와의 병합 문제가 생기는데, 이 도구의 사용 맥락에서는 그 복잡도를 감수할 이득이 없다고 판단했습니다. **충돌을 해결하는 대신 충돌이 발생할 수 없는 경계를 그었습니다.** 오프라인 상태에서 진실의 원천이 서버가 아니라 눈앞의 디바이스이기 때문에 성립하는 설계입니다.

**(b) 바이너리 ↔ UI 변환 계층 분리**

디바이스와 주고받는 데이터가 모두 바이너리였기 때문에, `{ type, value }` 형태의 태그드 유니온으로 정규화하고 타입별 변환을 단일 진입점에서 분기 처리했습니다. 타입 추가가 팀 내부에서만 발생하고 개수가 유한한 조건이었기 때문에, 런타임 확장을 위한 레지스트리 구조 대신 명시적 분기를 택했습니다. 신규 모뎀 모델 대응은 enum에 타입을 추가하고 변환 분기를 확장하는 선에서 끝나도록 UI 레이어와 변환 레이어를 분리했습니다.

## 주요 작업

- Web Serial API를 통한 USB 디바이스 직접 통신 핸들링
- 타입별 바이너리 디코딩 → UI 바인딩 → 재인코딩 → 기기 전송 파이프라인 설계
- 서비스 워커 기반 오프라인 모드 (앱 셸 캐싱, 모델별 기본 설정값 로컬 보관)
- 모델별 기본 설정값 일괄 적용 기능
- 다국어 지원

## 트러블슈팅

일반적인 오프라인 우선 앱은 서버 데이터를 캐시하고 로컬에서 수정한 뒤 나중에 병합하며, 여기서 충돌 해결이라는 난제가 발생합니다.

이 도구에서는 문제를 푸는 대신 **문제가 생기지 않도록 경계를 그었습니다.** 오프라인에서 수정 가능한 대상은 USB로 물리적으로 연결된 기기 그 자체로 한정하고, 서버를 통한 등록·수정은 기능 자체를 차단했습니다. 병합할 대상이 존재하지 않으므로 충돌도 존재하지 않습니다.

## 성과

사전 세팅 → 현장 오프라인 작업이라는 실제 업무 흐름에 맞춰 기능 경계를 나눴고, 엔지니어가 현장에서 네트워크 상태를 신경 쓰지 않고 동일한 흐름으로 작업할 수 있도록 했습니다. 바이너리 변환 계층을 분리해 신규 타입 추가 시 UI 코드 변경 없이 enum과 처리 분기 추가만으로 대응 가능한 구조를 유지했습니다.

정량 지표는 없습니다.

## 배운 것

프론트엔드는 보통 이미 JSON으로 정제된 데이터를 받습니다. 바이너리부터 다루면서 **프로토콜과 UI 사이의 변환 계층을 직접 설계**해본 것이 이 프로젝트의 가장 큰 소득입니다.

그리고 어려운 문제를 푸는 것보다 **그 문제가 생기지 않는 경계를 긋는 것**이 더 나은 답일 때가 있다는 걸 오프라인 범위 정의에서 배웠습니다.

## 아쉬운 점 · 다시 한다면

- **타입 누락에 대한 컴파일 타임 방어 부재** — 변환 분기에서 신규 타입 처리를 빠뜨려도 빌드가 통과하는 구조였습니다. 당시엔 타입 개수가 적어 리뷰로 커버된다고 봤지만, 모델이 늘어나면 결국 사람이 놓칩니다. `never` 타입을 활용한 exhaustiveness check를 추가하면 타입 추가 시점에 누락이 컴파일 에러로 드러나고, 잘못된 값이 물리 기기에 기록되는 리스크를 줄일 수 있습니다.
- **설정 덮어쓰기의 원자성** — 기본 설정 일괄 적용은 파괴적 작업인데, 전송 중 연결이 끊기면 기기가 부분 적용 상태로 남을 수 있었습니다. 적용 전 기존 설정을 로컬에 백업하고 실패 시 복원하는 절차가 필요합니다.
- **모델 불일치 검증** — 다운로드한 기본 설정값이 실제 연결된 기기의 모델과 일치하는지 확인하는 장치가 없었습니다. 잘못된 모델의 설정이 물리 기기에 기록되면 복구 비용이 크므로, 적용 직전에 기기에서 읽은 모델 코드와 설정값의 대상 모델을 대조하는 절차가 필요합니다.
