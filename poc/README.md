# RAG PoC Harness

`samples/`의 실제 콘텐츠로 청킹 경계와 검색 품질을 측정한다. 의존성 없이 표준 라이브러리만 쓴다.

```bash
python3 poc/rag_eval.py chunks     # 청킹 측정 (API 키 불필요)
python3 poc/rag_eval.py selftest   # 자체 검증 (API 키 불필요)
python3 poc/rag_eval.py search     # 임베딩 + 검색 평가 (OPENAI_API_KEY 필요)
```

Spring AI가 아니라 Python 스크립트인 이유는 이 코드가 제품이 아니라 측정 도구이기 때문이다.
여기서 얻는 결론(청크 크기, 경계 규칙, 모델 적합성)은 언어와 무관하게 이전된다.
제품 구현은 RAG_DESIGN대로 Spring Boot에서 한다.

## 측정 결과 — 2026-09-09

문서 6건 (공개 5 / 비공개 1), 본문 합계 약 13,400자.

| 전략 | 청크 수 | 최소 | 중앙 | 최대 | 200자 미만 | 1200자 초과 |
|---|---|---|---|---|---|---|
| A: 섹션 = 청크 | 46 | 88 | 268 | 647 | 11 | 0 |
| B: 짧은 섹션 병합 | 35 | 205 | 367 | 821 | 0 | 0 |

**가장 긴 섹션이 647자였다.** 섹션이 길어서 쪼개야 한다는 기존 가정은 이 콘텐츠 규모에서 틀렸다.
실제 문제는 반대였다. "정리", "시작", "개요" 같은 짧은 섹션 11개가 그대로 청크가 되면 검색 노이즈가 된다.

병합 후 35청크 중 **9개가 두 개 이상의 섹션에 걸친다**(`주의할 점 + 정리`, `시작 + HLS를 뺀 이유`).
따라서 `document_chunk.section_title`을 단일 컬럼으로 두면 출처를 정확히 표시할 수 없다.
DATA_MODEL을 `section_titles text[]`로 수정했다.

### 하네스가 함께 검증하는 것

- 관리자 전용 필드(`admin_note`, `open_questions`, `sample_note`)가 색인 본문에 섞이지 않는다 — DATA_MODEL 공백 5번
- 추천 질문 블록(`:::questions`)이 색인 본문에서 제거된다 — 근거가 아니라 UI 요소이므로
- 비공개 문서(`offline-first-boundary`)가 검색 대상에서 제외된다 — ADR-0005 결정 3, RAG-007

`selftest`가 이 세 가지를 assert로 확인한다.

## 아직 측정하지 못한 것

`search`는 `OPENAI_API_KEY`가 없어 실행하지 못했다. 다음이 미측정이다.

- text-embedding-3-small의 한국어 검색 품질
- 전략 A와 B의 실제 검색 정확도 차이
- `vector(n)` 차원 확정 (현재 DATA_MODEL의 1536은 후보값)
- 근거 없음 질문(RAG-003)에서 상위 결과의 유사도 분포

키를 넣고 아래를 실행하면 기대 출처 대비 적중을 출력한다. 임베딩 비용은 청크 35개 + 질문 7개로 1센트 미만이다.

```bash
export OPENAI_API_KEY=...
python3 poc/rag_eval.py search
```

## 한계

- 토큰이 아니라 문자 수로 잰다. 경계 비교에는 충분하지만 절대 토큰 예산 확인에는 tiktoken이 필요하다.
- pgvector를 쓰지 않고 메모리에서 코사인을 계산한다. 청크 수십 개 규모에서 인덱스는 측정에 영향을 주지 않는다. HNSW 파라미터 검증은 실제 DB가 생긴 뒤에 한다.
- 블로그 3편이 AI 초안이라 문체가 균질하다. 실제 원고로 교체하면 청크 길이 분포가 달라질 수 있다.
